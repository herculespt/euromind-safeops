# Fixed-check process supervision — 0.3.0a17

<!-- safeops-version: 0.3.0a17 -->

[Português (Portugal)](pt-PT/SUPERVISION.md)

Implemented in source 0.3.0a17. Public GitHub/PyPI 0.3.0a8 predates this capability.

Each approved fixed check gets an internal gated Python launcher. It starts no project code until the parent establishes native ownership and sends a one-byte start token. Actual check arguments, UTF-8 streams, disabled automatic import bytecode and schema-1/schema-2 targets remain fixed. The worker gets closed/empty stdin. No provider, shell, arbitrary command option, PID scan, external taskkill utility or runtime dependency is introduced.

POSIX uses a new process group in the parent's session. The launcher holds the group-ID PID while the check executes. After reaping its direct worker it leaves the group for the parent's group and publishes a bounded completion record, then waits for parent release. This lets the parent observe the owned group becoming absent while the launcher keeps its identity allocated. Signals target only this owned group before launcher reaping; the launcher is separately terminated through its owned child handle if required. Unsupported group operations or nondefault SIGCHLD disposition fail closed. Same-group descendants are covered; processes that deliberately create another group/session escape that boundary. This is cooperative supervision, not hostile-code isolation.

Windows uses an unnamed, noninheritable Job Object with kill-on-last-handle-close and no breakaway flag. The gated launcher's native process handle is assigned before release, so ordinary worker descendants join the job. Completion requires the job's active-process count to contain only the waiting launcher, then zero after release. Unavailable assignment/query/termination fails closed; there is no direct-process fallback. Initial support uses CPython's native Popen process handle and is validated on the supported Windows CI matrix.

The per-check timeout covers launcher startup after process creation, the worker and owned descendants, including children retaining stdout/stderr. OS process creation itself is not interruptible by this timer. A bounded additional cleanup interval follows timeout/cancellation/failure. POSIX sends TERM then KILL to the owned group before reaping the launcher; Windows terminates the job and verifies its active count. POSIX group absence is conservatively required, so unreaped descendant zombies can require explicit investigation. No successful receipt/automatic marker cleanup occurs when termination or stream closure cannot be established.

Two private daemon readers continuously drain binary stdout/stderr, retaining bounded tails only; no output is written to a file or receipt. Return at most the last 12,000 decoded UTF-8 characters per stream, replacing malformed/split characters and normalizing newlines. A child retaining a pipe cannot cause an unbounded communicate/wait. Unknown or escaped processes holding a pipe cause incomplete supervision and retained run state rather than success. Rare blocked readers can remain until their pipe closes or the parent process exits; repeated approved runs remain blocked by the retained marker.

Normal result requires the completion record, native ownership termination, launcher exit and both output readers at EOF. A confirmed timeout produces timed-out (subject to existing changed-input/context precedence). Operational/cleanup failure keeps intent without a final receipt; uncertain cleanup additionally retains run.lock. No approval is granted or renewed. Ordinary exceptions/KeyboardInterrupt attempt bounded owned cleanup first. Abrupt parent death retains run.lock and incomplete intent: Windows kill-on-close terminates job members; POSIX launcher attempts group termination on private control-pipe EOF, but no guarantee is made if that launcher also dies/is stopped or escapes are involved. Independent parent/child verification remains mandatory before recover-lock.

Records, guards, application-pending blocking and all Git/plan/approval/proposal/stage/run/application history are preserved. Runner protocol becomes 5 and native-lock protocol 3; upgrading requires fresh version-bound plans/proposals/approvals. No new release is published automatically. OS sandboxing, arbitrary-read allowlists, network/distributed supervision and authenticated provenance remain planned.

Primary references: [Python subprocess](https://docs.python.org/3.11/library/subprocess.html), [Python process groups](https://docs.python.org/3.11/library/os.html#os.setpgid), [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [assignment](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject), [accounting](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information), [termination](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject).

Bounds: existing 1–300-second check timeout, 3-second additional cleanup budget, 0.2-second POSIX TERM grace, 65,536 retained bytes plus an 8,192-byte read chunk per stream, 12,000 returned characters, and at most 1,024 bytes in the transient completion object (schema, launcher PID, random 32-hex token and exit code). Completion is atomically published in a private temporary directory and removed afterwards; it contains no project text. These are bounded waits/storage, not a hard real-time or OS resource quota. Native process creation/scheduling and uninterruptible kernel operations are outside the wall-clock guarantee. No output/coverage artifact is uploaded automatically.

The launcher starts with Python `-I`, excluding workspace/PYTHONPATH/user-site startup imports before the gate; the installed interpreter, environment and SafeOps package remain trusted. The actual fixed worker retains its original arguments and approved environment after native assignment.

Cleanup diagnostics use fixed phase/reason codes and optional numeric OS errno, never native exception text. A signal request can fail after processes have already exited (observed on macOS after TERM); cleanup still attempts reaping and independently requires native group absence/zero job members plus output EOF. Permission errors are never interpreted as absence: unavailable observations retain the marker.

Source 0.3.0a17 waits for final zero Windows job accounting within the same three-second cleanup budget used for launcher exit, EOF and failure cleanup. A transitional positive count cannot turn a completed failed check into an immediate operational error; persistent/unavailable confirmation remains fail-closed with retained state. Fixed-phase diagnostics exclude native exception text. Runner 5/lock 3 and schemas remain; the updated version/cleanup-policy binding requires fresh reviewed plans/proposals/approvals.
